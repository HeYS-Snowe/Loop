# APK 命名规范

## 1. 命名规则概述

### 1.1 基本格式
```
{程序名}_{状态类型}_{版本号}_{构建日期}_{构建序号}.apk
```

### 1.2 命名示例
```
MindCareAI_release_1.0.0_20260111_01.apk
MindCareAI_beta_0.0.1_20260111_02.apk
MindCareAI_fix_0.0.2_20260111_01.apk
MindCareAI_feature_0.0.3_20260111_01.apk
```

## 2. 命名元素详解

### 2.1 程序名
- **固定值**：`MindCareAI`
- **说明**：应用程序的名称，统一使用驼峰命名法

### 2.2 状态类型

| 状态类型 | 英文标识 | 中文说明 | 使用场景 | 完整性 |
|---------|---------|---------|---------|--------|
| 正式版 | `release` | 正式发布版本 | 经过完整测试，功能完整，可用于生产环境 | ✅ 完全体 |
| 测试版 | `beta` | 公开测试版本 | 功能基本完整，需要用户反馈测试 | ⚠️ 非完全体 |
| 内测版 | `alpha` | 内部测试版本 | 功能开发中，仅限内部测试 | ❌ 非完全体 |
| 候选版 | `rc` | 候选发布版本 | 准备发布前的最终测试版本 | ✅ 接近完全体 |
| 修复版 | `fix` | 问题修复版本 | 针对正式版的问题修复 | ✅ 完全体 |
| 紧急修复 | `hotfix` | 紧急修复版本 | 针对严重问题的紧急修复 | ✅ 完全体 |
| 功能版 | `feature` | 新功能版本 | 包含新功能开发的版本 | ⚠️ 非完全体 |
| 开发版 | `dev` | 开发中版本 | 日常开发过程中的构建 | ❌ 非完全体 |
| 调试版 | `debug` | 调试版本 | 用于调试的构建版本 | ❌ 非完全体 |

### 2.3 版本号
- **格式**：`{主版本}.{次版本}.{修订版本}`
- **规则**：遵循语义化版本控制（Semantic Versioning）
- **来源**：从 `pubspec.yaml` 文件中的 `version` 字段读取
- **示例**：`1.0.0`、`1.0.1`、`1.1.0`、`2.0.0`

#### 版本号递增规则
- **主版本**：不兼容的 API 修改
- **次版本**：向下兼容的功能性新增
- **修订版本**：向下兼容的问题修正

### 2.4 构建日期
- **格式**：`YYYYMMDD`
- **说明**：APK 构建的日期，便于追溯
- 示例：`20260111` 表示 2026 年 1 月 11 日

### 2.5 构建序号
- **格式**：两位数字，从 `01` 开始
- **说明**：当天第几次构建，便于区分同一天的不同构建
- **示例**：`01`、`02`、`03`

## 3. 状态类型详细说明

### 3.1 正式版
- **标识**：`release`
- **完整性**：✅ 完全体
- **使用场景**：
  - 经过完整的测试流程
  - 所有功能都已实现并测试通过
  - 无已知严重 bug
  - 可用于生产环境部署
- **命名示例**：`MindCareAI_release_1.0.0_20260111_01.apk`

### 3.2 测试版
- **标识**：`beta`
- **完整性**：⚠️ 非完全体
- **使用场景**：
  - 功能基本完整，但可能存在未发现的 bug
  - 需要用户反馈进行测试
  - 用于小范围公测
- **命名示例**：`MindCareAI_beta_1.0.1_20260111_01.apk`

### 3.3 内测版
- **标识**：`alpha`
- **完整性**：❌ 非完全体
- **使用场景**：
  - 功能开发中
  - 仅限团队内部测试
  - 可能存在已知问题
- **命名示例**：`MindCareAI_alpha_0.9.0_20260111_01.apk`

### 3.4 候选版
- **标识**：`rc`
- **完整性**：✅ 接近完全体
- **使用场景**：
  - 准备发布前的最终测试版本
  - 功能完整，等待最终确认
  - 如果无重大问题，将升级为正式版
- **命名示例**：`MindCareAI_rc_1.0.0_20260111_01.apk`

### 3.5 修复版
- **标识**：`fix`
- **完整性**：✅ 完全体
- **使用场景**：
  - 针对正式版的问题修复
  - 不包含新功能
  - 修复特定 bug 或问题
- **命名示例**：`MindCareAI_fix_1.0.0_20260111_01.apk`

### 3.6 紧急修复版
- **标识**：`hotfix`
- **完整性**：✅ 完全体
- **使用场景**：
  - 针对严重问题的紧急修复
  - 需要快速发布
  - 修复影响生产环境的严重 bug
- **命名示例**：`MindCareAI_hotfix_1.0.0_20260111_01.apk`

### 3.7 功能版
- **标识**：`feature`
- **完整性**：⚠️ 非完全体
- **使用场景**：
  - 包含新功能开发的版本
  - 功能可能未完全测试
  - 用于展示或测试新功能
- **命名示例**：`MindCareAI_feature_1.1.0_20260111_01.apk`

### 3.8 开发版
- **标识**：`dev`
- **完整性**：❌ 非完全体
- **使用场景**：
  - 日常开发过程中的构建
  - 功能开发中，不稳定
  - 用于开发调试
- **命名示例**：`MindCareAI_dev_1.1.0_20260111_01.apk`

### 3.9 调试版
- **标识**：`debug`
- **完整性**：❌ 非完全体
- **使用场景**：
  - 用于调试的构建版本
  - 包含调试信息
  - 性能可能较差
- **命名示例**：`MindCareAI_debug_1.0.0_20260111_01.apk`

## 4. 版本号管理规范

### 4.1 版本号格式
```
{主版本}.{次版本}.{修订版本}+{构建号}
```

### 4.2 版本号管理策略

#### 4.2.1 正式发布前版本号策略
- **策略**：在正式发布前，版本号格式为 `0.0.x`
- **版本结构**：
  - 主版本：固定为 `0`
  - 次版本：固定为 `0`
  - 修订版本：可根据需要递增（`0`、`1`、`2`...）
- **目的**：便于开发、测试和修复阶段的版本管理
- **适用范围**：所有非正式发布的版本
- **示例**：
  - 开发版：`MindCareAI_dev_0.0.0_20260110_01.apk`
  - 测试版：`MindCareAI_beta_0.0.1_20260110_01.apk`
  - 修复版：`MindCareAI_fix_0.0.2_20260110_01.apk`
  - 功能版：`MindCareAI_feature_0.0.3_20260110_01.apk`

#### 4.2.2 正式发布后版本号递增规则
正式发布后，按照语义化版本控制（Semantic Versioning）规则递增版本号。

##### 主版本递增
- **触发条件**：
  - 不兼容的 API 修改
  - 重大架构调整
  - 删除或重命名核心功能
- **示例**：`1.0.0` → `2.0.0`

##### 次版本递增
- **触发条件**：
  - 向下兼容的功能性新增
  - 新增重要功能模块
  - 功能增强但不影响现有功能
- **示例**：`1.0.0` → `1.1.0`

##### 修订版本递增
- **触发条件**：
  - 向下兼容的问题修正
  - Bug 修复
  - 性能优化
  - 小改进
- **示例**：`1.0.0` → `1.0.1`

### 4.3 构建号管理
- **格式**：从 `1` 开始递增的正整数
- **说明**：每次构建自动递增
- **来源**：从 `pubspec.yaml` 文件中的 `version` 字段读取（`+` 号后面的部分）
- **示例**：`1.0.0+1`、`1.0.0+2`

## 5. 构建序号管理

### 5.1 构建序号规则
- **格式**：两位数字，从 `01` 开始
- **递增规则**：同一天内每次构建递增
- **重置规则**：每天重置为 `01`

### 5.2 构建序号示例
```
20260111_01  # 当天第一次构建
20260111_02  # 当天第二次构建
20260111_03  # 当天第三次构建
20260112_01  # 第二天第一次构建（序号重置）
```

## 6. 命名规则应用场景

- **推荐状态**：`release`
- **命名示例**：
  - `MindCareAI_release_1.0.0_20260111_01.apk`

  - `MindCareAI_beta_1.1.0_20260111_01.apk`

## 7. 命名规则最佳实践

### 7.1 版本发布流程
```
dev → alpha → beta → rc → release
```

### 7.2 问题修复流程
```
发现问题 → hotfix/fix → 测试 → release
```

### 7.3 功能迭代流程
```
dev → feature → alpha → beta → rc → release
```

### 7.4 命名一致性
- 同一项目使用统一的命名规则
- 版本号与代码仓库标签保持一致
- 构建日期与实际构建时间保持一致
- 构建序号按顺序递增，不跳号

### 7.5 命名可追溯性
- 通过命名可以快速识别 APK 的版本和状态
- 通过构建日期和序号可以追溯构建历史
- 通过状态类型可以了解 APK 的用途和完整性

## 8. 自动化脚本

### 8.1 重命名脚本
项目提供了自动化重命名脚本 `rename_apk.ps1`，位于 `mindcare_app/scripts/` 目录。

### 8.2 使用方法
```powershell
# 重命名所有 APK
cd mindcare_app\scripts
.\rename_apk.ps1

# 重命名指定状态的 APK
.\rename_apk.ps1 -Status release

# 重命名指定版本的 APK
.\rename_apk.ps1 -Version 1.0.0
```

### 8.3 脚本功能
- 自动读取版本号
- 自动生成构建日期
- 自动生成构建序号
- 支持自定义状态类型
- 支持批量重命名
- 自动备份原文件

### 10.2 常见问题

**Q: 为什么需要构建序号？**
A: 同一天可能构建多次，构建序号可以区分不同的构建版本。

**Q: 状态类型可以自定义吗？**
A: 可以，但建议使用本文档定义的标准状态类型，以保持一致性。

**Q: 版本号如何管理？**
A: 建议使用语义化版本控制，并在 `pubspec.yaml` 文件中维护。

**Q: 如何追溯历史版本？**
A: 通过构建日期和序号可以追溯构建历史，同时建议在代码仓库中使用标签标记重要版本。
